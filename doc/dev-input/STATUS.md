# Input devices (issues #190 and #193): status and running memory

Amiga mouse and Atari CX30 paddles, selectable per port in the on-screen menu, and a right click with the MEGA key for Amiga mice. `SPEC.md` is the design, `RESEARCH-amiga-mouse.md` and `RESEARCH-paddles.md` are the facts behind it. This file records the state of the work, the decisions, the verification and what is open.

## 0. State

* The work is WIP-V6-A26. It was developed on the branch `mh_implement_190_193` (branched from `develop` at `6845596`, WIP-V6-A25), merged into `develop` on 2026-11-18 as `f87e0cb` and released as Alpha 26; the branch is deleted.
* Everything is implemented, simulated and reviewed, and the Vivado build of R3 and R6 from `69d0f51` passed (section 6). On hardware the owner tested the release, and the reporters of both issues confirmed it: Amiga mice work in the setting "Amiga" (issue #190, closed), and Atari paddles use twice the rotation in the setting "Atari CX30" (issue #193, closed on 2026-11-19; section 7).
* Issue #266 (2026-11-22, "the mouse setting does not follow `Flip joystick ports`") is no defect: the settings belong to the socket (D1) and move with the device. The reported symptoms appear exactly when `Amiga` is set for the socket with the joystick. Analysis, end-to-end bench and the open questions to the reporter: `issue266/README.md`.
* After the release, `develop` got a bus skew constraint for the crossing of the paddle values with a sign-off check in the build scripts (section 8); the build of 2026-11-19 confirms it (section 6). It changes no logic and comes with the next version.

## 1. Decisions

| # | Decision | Why |
|---|---|---|
| D1 | "Port 1" and "Port 2" in the two submenus are the sockets of the MEGA65; the setting travels with "Flip joystick ports". | The setting describes the device that is plugged in. |
| D2 | The user selects the device; nothing is detected automatically. | The autodetection of the MEGA65 core has false positives and lets quadrature through to the keyboard before it has decided (mega65-core issues #963, #779, #549). |
| D3 | A new decoder (`amiga_mouse.vhd`) on the raw pins in the core clock domain; the Amiga part of the MEGA65 module `mouse_input.vhdl` stays switched off. | The debouncer swallows the quadrature (the experiment of 2022 on branch `dev-amigamouse` ran through a 5 ms filter, which explains its result); decoding in the core clock domain needs no crossing of a multi-bit position. The Amiga core for the MEGA65 (AExp) reads the same raw lines with success. |
| D4 | The mouse is presented as a 1351: POT value = 64 + position with bit 0 clear; two counts of the mouse are one position unit of a 1351 driver. | Format of a real 1351; scale of the MEGA65 core and of VICE, so the same mouse feels the same in both cores. An exported bit 0 would make the drivers lose half a unit at every call with an odd difference. |
| D5 | Rate limiter: one step per 400 µs, backlog of 127 counts. | A 1351 driver takes 63 or more steps between two calls as a movement in the other direction; fast optical mice would reach that at 8 cm/s. |
| D6 | The right and the middle button of the device are read only from a mouse or adapter that holds pins 9 and 5 high while the buttons are released, found out by observation (a value below 128 has been confirmed); a button that is pressed for 5 s is released. | The board cannot tell an open pin from a grounded one. The release covers the exchange or the unplugging of such a device; it is 5 s and not the 30 s of the Amiga core because the two buttons are the up and down lines, which C64 port 1 shares with the keyboard. The Amiga core for the MEGA65 (AExp) uses the same mechanism in the field. |
| D7 | The direction lines of a port in Amiga mode are hidden from the C64. | On port 1 they are in parallel with the keyboard matrix. |
| D8 | Atari paddles: the count of a longer window, halved (factor 2, window of 510 ticks, cycle of 769 ticks). The cycle is only long while a port is set to Atari, and a port in C64 mode is always counted in the same 255 ticks. | A ratio is independent of the board. A 1 MOhm paddle then reads like a 500 kOhm one. With all settings at "C64" the measurement is the same as before, and a 1351 on a port in C64 mode always sees its window. |
| D9 | The four paddle values cross into the core clock domain through `cdc_stable` instead of per-bit synchronizers. | Found during the analysis: a read of the SID register in the clock cycle of a change could return a value that was never measured (a 1351 jumps by up to 32 units). |
| D10 | Menu: section "Input Devices" in "Advanced Settings" with the submenus "Keyboard Shortcuts", "Mouse" and "Paddles"; the two new submenus have a headline, the two items of port 1, a line, the two items of port 2, a line and "Back", and the Mouse submenu has the switch of D14 behind the Amiga item of each port; no `%s` summary on the openers. | Layout asked for by the owner; the line between the ports is an addition. |
| D11 | The 1 ms debouncer stays as it is for the setting "C64". | A 1351 only sends its buttons over the debounced lines; the devices that the filter breaks (section 6 of `RESEARCH-amiga-mouse.md`) also need the core to drive the port lines, which it does not do. |
| D12 | The four comparator inputs of the paddle measurement get a two-stage synchronizer. | Found during the work on the Atari mode: they went straight from the pins into the count enables of multi-bit counters. The measurement moves by 40 ns, far less than one count of 1 µs. |
| D13 | No change of the timing constraints. | The new crossing of D9 sits on a clock pair that `CORE/CORE.xdc` declares a false path, so it is not timed (section 8). A constraint needs a Vivado run to be validated, which was not available. |
| D14 | A switch per port, "MEGA+left = right", is the substitute for the right button: off by default and shown only while the port is set to "Amiga". A press of the left button that begins while the MEGA key is held is the right button (the up line), and the fire line stays released. The C64 keeps seeing the MEGA key as its Commodore key. | Decided by the owner on 2026-11-17. Most Amiga mice have no right button on this board (D6). The key alone cannot be the button, because the C64 needs its Commodore key. C64 programs rarely use the right button, so the switch is off by default. |
| D15 | The key at the moment the button goes down decides for the whole press: one flip-flop per socket follows "Amiga mode, switch on, key held" while the debounced fire line is released and keeps its value while the line is pressed; the fire line and the up line stay combinational functions of it. | A swap that followed the key in every clock cycle would end a right click with a left click whenever the key is released a moment before the button. A decision that is only registered at the edge of the fire line would put a pulse of one clock cycle on that line, which a program that polls the CIA in a loop can catch. |
| D16 | The state of the MEGA key comes from the key scan without a filter of its own. | A disturbed frame of the keyboard link shows a key as pressed for one or two scans (1.1 to 2.2 ms). The C64 sees such a frame as a Commodore key in every version; the new consequence, a left click that becomes a right click, needs the start of the click inside that window. The state of Caps Lock has its 4 ms filter because it acts for as long as it is set. |
| D17 | `MENU_HEAP_SIZE` is 5,696 words. | The two switches need 56 words, which would have left 158 of 5,632 free at peak; the heap check of `menu_test.py` asks for 180. 5,696 is the next multiple of 64 and leaves 222; every word is taken from the heap of the file browser. |

No other constant moved.

Menu heap and stack per menu line: a line costs its characters plus 6 words of menu heap (the two switches: 28 words each), two stack words on the chain of a load in the visible menu and one on the chain of a keyboard shortcut. The firmware of the menu with 325 lines differs from the one with 323 lines in 15 words, the immediate values of `MENU_HEAP_SIZE` (10) and `HEAP_SIZE` (5).

Right click with the MEGA key: the key scan visits every key once per 1.11 ms (80 keys of 438 clock cycles), and one frame of the serial keyboard link takes 0.46 ms. `mega_key_n_o` follows a press of the key within 1.6 ms and a release within 2.7 ms (measured with the model of the keyboard: 0.13 to 1.45 ms and 1.22 to 2.58 ms). The debounced fire line follows the button by 1 ms, so the key decides as it is seen about 1 ms after the button went down.

Amiga mouse at the core clock of 31,527,778 Hz: glitch filter 63 clock cycles (a pulse of up to 63 periods never passes, a level of 65 always does), one step per 12,610 cycles (399.96 µs), confirmation of a button 10 steps (4.0 to 4.4 ms), release of a stuck button after 12,500 steps (5.0 s). At 2,400 counts per second the backlog holds 2 counts at most and the position follows within 0.53 ms. A PAL frame sees at most 50 steps and an NTSC frame 44; a 1351 driver misreads from 63 on. In NTSC mode all times are 3.7 % shorter.

Paddles: with t the time from the end of the discharge to the change of the comparator output, a port in C64 mode reads `min(255, max(0, floor((t + 40 ns) / 1 µs) - 1))` and a port in Atari mode half of the same expression with 510 instead of 255, rounded down. A short cycle has 514 ticks of 1 µs, a long one 769.

## 8. Open points

* **Timing of the paddle crossing: settled by a bus skew constraint.** `CORE/CORE.xdc` declares the QNICE clock and the core clock a false path in both directions, which outranks the `set_max_delay` that `M2M/common.xdc` attaches to every `cdc_stable`. The 32 paths of `i_qnice2main_paddles` are therefore not timed (neither were the per-bit synchronizers before). `cdc_stable` delivers consistent values as long as the 32 bits arrive within one core clock period (30 ns) of each other, which the routes of a small bus satisfy by a wide margin: in the R6 build of 2026-11-17 the two paths that the timing report lists are 0.1 ns of wire between neighboring slices. As agreed with the owner, that margin is a checked property now: `CORE/CORE.xdc` has a `set_bus_skew` of 10 ns from the 32 source registers (`input_reg_gen.src_data_reg[*]`) to the 32 first destination registers (`cdc_stable_gen.dst_data_d_reg[*]`). A bus skew constraint is an assertion and not a timing exception, so the false path does not override it; only `route_design` works on it; and a violation shows neither in WNS nor in WHS, only in `report_bus_skew` (the project runs already write that report after routing and after the last `phys_opt_design`, for the 20 constraints that the XPM FIFOs bring along). Therefore `CORE/signoff_gates.tcl` has two checks: `signoff_gates` wants both patterns of the constraint to match 32 cells, and the new `signoff_bus_skew` reads `report_bus_skew` of the routed design and fails the sign-off if any bus skew constraint is violated or if the one of the paddle crossing is missing, covers fewer than 32 endpoints or has another requirement than 10 ns. `build_bitstream.tcl` and `reroll_bitstream.tcl` call it on the design the bitstream is written from. Section 6 has the numbers of the build that confirms it: a spread of about 1.2 ns. No other `cdc_stable` is instantiated directly between these two clocks.
* **The right click with the MEGA key on C64 port 1.** The up line of port 1 is a line of the keyboard matrix, so every right button of a 1351 in port 1 looks like the keys of one matrix row to a program that scans the keyboard. With the MEGA key held, the C64 sees them together with its Commodore key: at the BASIC prompt a right click changes the text color instead of typing a digit. Programs that use the mouse read the port themselves; the hardware test has a step for it. Port 2 has no such effect.
* **The state of the MEGA key is not filtered** against a disturbed frame of the keyboard link (D16); the rate of such frames on the hardware is not known.
* **USB adapters with a polled wheel protocol** (Micro Tom) may make the pointer twitch, because every discharge of the paddle pins looks like a request to them; the Amiga core has the same effect and the cure (wire 5 cut).
* **A 1351 on one port while the other port is set to "Atari CX30"** sees a measuring cycle of 769 µs instead of 514 µs; by the description of its controller that is harmless, but it is untested.
* **The scale of the Amiga mouse** (two counts per position unit) and the rate limit are generics of `amiga_mouse.vhd`; the hardware test decides whether they feel right.

## 10. How the work was organized

A controller wrote the specification from two research reports (all links of both issues, the sources of the MEGA65 core and of the Amiga core, the board schematics) and from the code, and one implementing agent per part worked on a private clone: menu and firmware, the Amiga mouse with the wiring, the paddle measurement, the program for the hardware test, and the full-system simulation. Every design change was then reviewed by an independent agent on a clone of its own, which got the specification and the commits and nobody's conclusions, wrote mutants of its own and reported; its findings went back to the implementing agent. The controller integrated the commits and ran all suites on the integrated tree.

The right click with the MEGA key was added on 2026-11-17 in the same way: the specification first, one implementing agent for the menu and the firmware budgets, one for the logic and its benches, one for the full-system simulation, and one independent reviewer for each of the two changes. The reviewers found no defect and several gaps of the tests, which went back to the implementing agents and were closed with the firmware unchanged.
