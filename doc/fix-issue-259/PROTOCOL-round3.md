# REU 1764 tests, round 3 (for Joe3f00ff)

Hi Joe, thank you for the round-2 PDF, it was exactly what we needed. In short: Alpha 23 does fix the lost bytes in copies from the REU to the C64 (`1-FETCH` is clean on A23 and lost one byte per interruption on A22, as predicted), copies into the REU are clean, the data in the REU survives, and the one thing that breaks is the REU's **verify** command: every verify that the VIC-II interrupts reports a fault, on A22 and A23 alike, whatever the data. The strange part is that the "Bit Fill" step of the CMD test runs more than a thousand such verifies with the screen on and never faults, while every other verify in the same program and in our BASIC tests does. We now know exactly what Bit Fill does (we decoded the CMD program), and the five programs below reproduce it piece by piece and look at the fault from new angles. They print their own verdicts; please photograph the final screen of each.

**Setup:** the five programs below run on **Alpha 23** (they measure what the REU does, so the version must stay the one we have data for); Alpha 24 comes in at the end. Simulated REU **off** (as in your round-2 config), display mode as usual. Two of the programs contain machine code; they load and start like the others.

**Disk:** `reu-tests3.d64` (attached). Mount it, then `LOAD"8-SWAP",8` and `RUN`, and so on. Each program takes between 20 seconds and 2 minutes.

1. `8-SWAP`: the only thing Bit Fill does that none of our failing tests did is an REU "swap" command before its verifies. This program runs the 16 KB verify that always faulted in round 2, then does a tiny swap, then the verify again, and so on with bigger swaps. If the verify suddenly passes after a swap, we have the key to the Bit Fill mystery.
2. `9-VALUES`: 256-byte verifies with the screen on, 50 each, for eight different fill values (`$FF`, `$00`, `$AA`, `$55` and four others). We expect about 17 faults per value, except that one theory says the value `$FF` can never fault. Please photograph the full list.
3. `10-AFTER`: after each faulting verify it reads the REU's address registers (which byte the verify stopped at) and then copies the data back from the REU with the screen off and checks every byte. This tells us whether the verify merely reports a false fault or whether the data in the REU was damaged. Expected lines: `RUN n FAULT AT BYTE k LEN l ST s` followed by `REU DATA INTACT` or a list of wrong bytes. The last line is a control with one byte deliberately changed; it should report byte 100.
4. `11-BITFILL`: the exact CMD "Bit Fill" sequence in machine code (same addresses, same commands, same sprites, same timing), for one pattern on one bank, then seven variations that each leave one element out (no swap, no sprites, interrupts enabled, and so on), and finally the exact sequence again with one byte deliberately changed by the CPU before each verify, once with the screen on (8) and once with the screen off (9). Each line reports `r` and `c` (how many of the 4 verifies of each kind faulted), `cpu` (failed CPU checks) and `1st` (where the first fault happened). Variation 0 should show `r 0 c 0` if we reproduced Bit Fill correctly, and variation 9 must show `r 4` if its verifies compare anything at all; if it shows `r 0`, the famous Bit Fill immunity is just a verify that silently does nothing, which would explain everything.
5. `12-POSITION`: machine code that starts a 256-byte verify at a precisely chosen raster line, ten times just before a VIC-II interruption (line 50) and ten times at a line where no interruption can happen (line 52), and prints for each run the status, the byte at which the verify stopped, how many cycles the transfer took and the raster line at which it ended. This is the closest we can get to a logic analyzer with software. It shows the line-50 results first and waits for a key: please photograph that screen, press a key, then photograph the line-52 screen.

**Then Alpha 24 (attached as `C64MEGA65-WIP-V6-A24.zip`):** it contains a candidate fix built on the floating-bus theory. In the first cycle after the VIC-II takes the bus, the core now hands the REU the byte it asks for, for reads as well as for writes (Alpha 23 did this only for writes, which is what cured the fetches). Please run on A24: `3-VERIFY` from the round-2 disk, `9-VALUES` from this disk, and your patched CMD REUTEST with the screen on. If all three show zero faults and every CMD step says OK, the theory and the fix are confirmed in one go. If the faults stay, A24 behaves exactly like A23 otherwise, and the round-3 results on A23 tell us where to look next.

**One more thing, with a stopwatch:** when you next run the CMD test with the screen on, please time the "Bit Fill Pattern" line from `(00)` to `OK`. If all of its transfers really run it takes about 64 seconds; about 46 seconds would mean its verifies are being skipped.

If something hangs, press RUN/STOP+RESTORE or reset; nothing is written to the SD card.
