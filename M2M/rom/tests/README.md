MiSTer2MEGA65 firmware testbeds
===============================

This folder contains headless tests for the M2M QNICE firmware. Almost everything here runs in the QNICE **emulator** on your development machine — no MEGA65 hardware, no JTAG cable and no Vivado synthesis needed. The one exception is the string ROM test on simulated hardware, which needs devices that the emulator does not have and therefore simulates the real hardware with ghdl. The flagship is the **menu test suite** (`menu_test.py` plus five assembly testbeds), which verifies the on-screen-menu structure algorithms, dependency handling, submenu state machine and fast live-text updates of `../menu.asm`, including the multi-level (nested) submenus introduced with M2M V2.1.0.

Quick start
-----------

One-time setup per machine (the QNICE submodule ships prebuilt Linux binaries; on macOS rebuild them — note that a submodule checkout reverts this):

```bash
cc M2M/QNICE/assembler/qasm.c -o M2M/QNICE/assembler/qasm
cc M2M/QNICE/assembler/qasm2rom.c -o M2M/QNICE/assembler/qasm2rom -std=c99
( cd M2M/QNICE/emulator && bash make.bash )
```

Then, from anywhere in the repository:

```bash
python3 M2M/rom/tests/menu_test.py run      # the full menu test suite
python3 M2M/rom/tests/menu_test.py verify   # cross-check config.vhd/mega65.vhd
python3 M2M/rom/tests/strrom_test.py        # string ROM: build and static checks
python3 M2M/rom/tests/strrom_sim_test.py    # string ROM on simulated hardware (needs ghdl)
python3 M2M/rom/tests/bankdepth_test.py     # register bank depth of the firmware (static analysis)
```

Both commands must pass before you synthesize a bitstream after touching `menu.asm`, `menu_struct.asm`, the menu-related parts of `options.asm`, or the menu definition in `CORE/vhdl/config.vhd`.

How the menu test suite works
-----------------------------

The heart of the suite is the **golden model** in `menu_test.py`: instruction-level Python ports of the assembly routines (the structure builder, the boot-time validator, dependency handling, the `%s` summary walk, and a simulator of the whole `OPTM_RUN` navigation state machine). Four testbeds dump traces which `menu_test.py` compares character by character with independently computed output. The focused live-text testbed checks its API and lifecycle invariants in assembly and emits success markers which the same runner verifies.

`run` executes five testbeds:

* **`menu_struct_test.asm`** — feeds synthetic `OPTM_GROUPS` arrays (including the complete current menu from `config.vhd`, nested and adjacent regions, empty regions, a 10-level-deep chain, and every authoring-error fatal) to the pure routines `OPTM_STRUCT_BUILD`, `OPTM_STRUCT_VAL` and `OPTM_SUMM_SCAN` and dumps the resulting structure arrays at **every** menu level, the validation verdicts and the summary-scan results.
* **`menu_equiv_test.asm`** — the **no-breaking-changes regression gate**: it contains a verbatim copy of the pre-V2.1.0 toggle parser (`_OLDSTR`) and runs it side by side with the new bracket parser over 157 legacy-shaped fixtures (the real pre-V6 C64 menu plus 150 seeded-random legacy configs) at every level. The structure arrays must match **word for word** — this mechanically proves that existing M2M cores keep working unchanged.
* **`menu_nav_test.asm`** — drives the real `OPTM_RUN` of `../menu.asm` with scripted key sequences through the full C64 V6 menu and synthetic scenarios for enter-scan and live-dependency corner cases. It covers nested submenu entry and exit, cursor wrap-around, the jumps to the first and last item (Cursor left/right, including a dependency-hidden first item), radio/single-select semantics, simulated background redraws, dependency-driven redraws, and menu-level persistence across close/reopen. All screen functions of the init record are stubbed; a scripted `OPTM_FP_GETKEY` prints one state line per keypress, and the diff against the simulator trace catches any divergence. The testbed also feeds the real `OPTM_ITEMS` strings (with the `\n` stored as two characters, exactly like a VHDL string) and traces every `%s` callback as a `W I=<line>` line: this pins the `%s` scanner of `OPTM_SHOW` to the correct line indices and guards against the percent-terminated-label desync bug found during V6 hardware bring-up (labels like ` 100%` used to swallow the backslash of their newline and shift every later `%s` onto the wrong menu line).
* **`optm_deps_test.asm`** — exercises dependency resolution, validation, visibility and summary scanning against synthetic fixtures and the independently computed dependency model. One synthetic menu has the maximum size of 512 items, with dependency mothers at the flat indices 255, 256, 400 and 511; besides the testbed comparison, `run` checks its visibility against hand-derived expectations (`WIDE_VISIBLE`), because a limit shared by the golden model and the assembly would otherwise go unnoticed.
* **`optm_live_test.asm`** — drives the full `OPTM_RUN` loop and verifies `OPTM_LIVE_TEXT`: exact fixed-width replacement, register preservation, direct-paint coordinates, hidden-line and closed-menu backing updates, invalid-input no-ops, plus suppression and restoration of direct painting around selection callbacks.

The fixture files (`*_fixtures.asm`), the expected outputs (`*.exp`) and the assembler artifacts (`*.lis/*.out/*.rom/*.def`) are generated; they are gitignored and regenerated by every `run`.

Testing your own core (framework users)
---------------------------------------

If you build your own M2M core, you define your menu in `CORE/vhdl/config.vhd` (`OPTM_ITEMS`/`OPTM_GROUPS`) and mirror the flat line indices as `C_MENU_*` constants in `CORE/vhdl/mega65.vhd`. Keeping the three in sync by hand is the classic source of "the menu toggles the wrong feature" bugs — `menu_test.py` automates exactly this:

1. **Describe your menu once in the golden model.** At the top of `menu_test.py`, replace the contents of `V6_MENU` with your menu: one `(label, group name or None, [flags])` tuple per `OPTM_ITEMS` line, and put your group ids into the `G` dict. The flag names (`STDSEL`, `LINE`, `HEADLINE`, `SINGLESEL`, `MOUNT_DRV`, `HELP`, `LOAD_ROM`, `START`) and the submenu markers (`OPEN`, `CLOSE`) map 1:1 to the `OPTM_G_*` constants of `config.vhd`. Nesting works the way you would write it in `config.vhd`: place a complete `OPEN` … `CLOSE` block inside another one.
2. **Describe your `C_MENU_*` constants.** Replace the `C_MENU` table with your constant names, each referencing a group name and the ordinal of the member within that group — the model derives the flat index itself, so you never type an index manually. Adjust `osm_scaling_range()`/`volume_indices()` (or remove them) to match the subtypes your `mega65.vhd` uses.
3. **Run `python3 M2M/rom/tests/menu_test.py verify`.** It parses your `CORE/vhdl/config.vhd` and `CORE/vhdl/mega65.vhd` (the standard M2M directory layout) and reports every mismatch: wrong `OPTM_SIZE` or `OPTM_DY` (it computes the height of the largest menu view for you), a label/group word at the wrong index, unbalanced submenu brackets, or a `C_MENU_*` constant pointing at the wrong line. `vhdl` prints the derived constants if you prefer to paste instead of check.
4. **Run `python3 M2M/rom/tests/menu_test.py run`.** Your menu from step 1 automatically becomes a fixture of the structure testbed (it is built and checked at every submenu level) and the menu navigated by the first nav scenario. If your menu structure trips any of the firmware validations, you will see it here — at emulator speed, not after a 30-minute synthesis. Note that the navigation key script is written against the C64 V6 menu; if your menu differs structurally, either adapt `nav_script()` (the `until(...)` helper makes this mostly declarative) or rely on the structure/equivalence testbeds plus `verify`, which are menu-agnostic.

The other testbeds
------------------

* **`cfm_test.asm`** plus its runner **`cfm_test.py`** and testbench **`cfm_tb.vhd`** — regression gate for the 512-bit menu state register `M2M$CFM_ADDR`/`M2M$CFM_DATA` (one bit per menu item, 32 banks of 16 bits). The QNICE emulator has no M2M registers, so this test runs on simulated hardware instead: the runner builds the testbed as a self-contained ROM (QNICE Monitor at `0x0000`, like the release Shell), simulates the real QNICE CPU inside the real `M2M/vhdl/QNICE/qnice.vhd` with ghdl and checks the 5-bit bank selector, 32 distinct banks, `M2M$SET_SETTING`/`M2M$GET_SETTING` for all items from 0 to 511, and `ROSM_REM_OLD`/`ROSM_CHANGES` including the size of `OLD_SETTINGS`. The routines under test are copied verbatim from `tools.asm` and `options.asm` on every run, and the variables are the real ones from `shell_vars.asm`. Run it with `python3 cfm_test.py` (about 20 seconds; needs ghdl, skips without it).
* **`rosm_save_test.asm`** plus its runner **`rosm_save_test.py`** — regression gate for the write-cache loop of `ROSM_SAVE` (`../options.asm`), which walks all virtual drives before the on-screen-menu settings are saved. `VD_DRV_READ` returns its result in R8, the very register that carries the virtual drive number into it, so using R8 as the loop counter froze QNICE the moment the menu was closed on a core with two or more virtual drives (upstream M2M issue #58). The testbed replays the loop against a stub that reproduces that destructive R8 behavior and is built in two variants: the current loop must terminate for 1 to 15 drives and must still detect a dirty write cache, while the pre-fix loop must terminate for one drive and hang for two. Run it with `python3 rosm_save_test.py`.
* **`summary_test.asm`** plus its runner **`summary_test.py`** — C64-specific: the custom `SUBMENU_SUMMARY` callback of `CORE/m2m-rom/m2m-rom.asm`, which renders the main-menu lines `Model: %s` (turbo), `Kernal: %s` (JiffyDOS drive ROMs) and `Volume: %s` (Stereo Mix tag while a stereo SID is selected, issue #247). Nothing is mirrored by hand: the runner copies the real callback, `M2M$RPL_S` and the summary data out of the sources into `summary_test_gen.asm`, assembles them with the real `../menu.asm` and feeds the menu of `menu_test.py` (`V6_MENU`) and the `C_MENU_*` constants of `mega65.vhd`. Over 200 cases (every SID setup x Stereo Mix x several volumes, every volume label, every Model and Kernal combination, every other `%s` opener) are compared with an independent Python model, and every call checks the register contract. `python3 summary_test.py mutants` runs broken copies of `m2m-rom.asm` that must all be rejected. Do not run it at the same time as `menu_test.py`: both assemble in this folder, and the assembler wrapper uses one fixed temporary file. Run both after touching `SUBMENU_SUMMARY`, the Volume, SID, Model or Kernal submenus, or their `C_MENU_*` constants (`menu_test.py verify` first).
* **`crt_unload_test.py`** — test of unloading a `.crt` with `Space` on the `CRT:` line (GitHub issue #153). The script cuts the real routines out of the sources (the heads of `HANDLE_MOUNTING` and `LOAD_IMAGE` in `../shell.asm`, `CRTROM_M_UNLD` and `CRTROM_G_ID` in `../crts-and-roms.asm`, `UNLOAD_CRTROM` and `OSM_SEL_PRE` in `CORE/m2m-rom/m2m-rom.asm`), links them against stubs that print every access to the hardware (CSR registers of the CRT/ROM devices, `M2M$CSR`, virtual drives, settings) and to the menu, runs 861 cases in the emulator and compares the trace with an independent model: which key on which line unloads, the order "hold the C64 in reset, check the drives for unsaved data, set the CSR status to idle, wait for the parser of the same device, release the reset", the dirty-cache and "Use hardware slot" rules, the time limit of the wait, register preservation, and that `LOAD_IMAGE` sets a device to "loading" only after the core accepted the file. Then it applies 21 mutants to the extracted code, each of which must be caught. Run it with `python3 crt_unload_test.py`.
* **`mount_reject_test.py`** — test of what a file that the core rejects leaves behind. `PREP_LOAD_IMAGE` can reject the file that the user selected (the C64 core rejects a disk image of the wrong size and a `.crt` that is too large); then neither the mounted image nor its menu line may change. `LOAD_IMAGE` checks a disk image with the scratch file handle `_DIRBR_FH` before it opens the file with the file handle of the drive (`HNDL_VD_FILES`), because `FLUSH_CACHE` writes the drive back through that handle, and `HANDLE_MOUNTING` writes the name into the menu line (the slot in `OPTM_HEAP` and its "%s is replaced" flag) only after `LOAD_IMAGE` succeeded. The script cuts all of `HANDLE_MOUNTING` and `LOAD_IMAGE` without the copy loop out of `../shell.asm`, links them against stubs that print every `f32_fopen` with its file handle, every call of `PREP_LOAD_IMAGE`, the CSR writes, `VD_STROBE_IM` and the menu calls, runs a session of 15 cases in the emulator (mounted, empty and preselected drives, direct mode, loaded and empty CRT/ROM lines, rejected files followed by Run/Stop or by an accepted file, names that fit into the menu line or get an ellipsis, files that cannot be opened) and compares the trace and a dump of the file handles, the mount and load status, `VD_NXT_INFO` and every menu line slot with an independent model. Then it applies 11 mutants, among them the reversal of each half of the fix; each must be caught. Run it with `python3 mount_reject_test.py`.
* **`saving_text_test.py`** — test of the menu line of a virtual drive while its write cache is dirty. The line shows `<Saving>` (`OPTM_S_SAVING`): `OPTM_CB_SHOW` in `../options.asm` parks the text of the line in the parking slot of the drive behind the `%s` slots of `OPTM_HEAP` (the slot of drive n is at `@OPTM_HEAP_LAST + n x @SCR$OSM_O_DX`) and copies it back when the cache is clean, and `HELP_MENU` reserves one parking slot per drive in its check of the heap budget. The script cuts `OPTM_CB_SHOW` with `_OPTM_CBS_REPL`, the budget check of `HELP_MENU`, `M2M$RPL_S` from `../tools.asm` and the block of `HANDLE_MOUNTING` in `../shell.asm` that stores the file name in the slot out of the sources and links them against stubs for the virtual drives, the CRT/ROM items, the submenu summary, `LOG_HEAP2`, `FATAL` and the string windows of `config.vhd` (the texts come from `CORE/vhdl/config.vhd`). It runs two configurations in the emulator, two drives with the menu width 27 of this core and three drives with width 20: budget cases with a heap that is large enough, exactly large enough or one word too small, then sessions with drives that save at the same time and finish in every order, one drive alone, redraws while dirty, names that fit, get an ellipsis or have the longest form that `HANDLE_MOUNTING` stores, empty drives, loaded and empty CRT/ROM lines and submenu lines. After every step the testbed dumps all slots, the parking slots and a guard area around them word by word; the complete trace, with the registers, the stack pointer and the register bank after every call, is compared with an independent model. Then it applies 10 mutants (the single buffer of all drives in either path, a wrong base or multiplier of the parking slot, one parking slot too few or too many in the budget, among others); each must be caught. Run it with `python3 saving_text_test.py`; `--keep` keeps the work folder with the testbed and both traces.
* **`next_disk_test.asm`** plus its runner **`next_disk_test.py`** — tests the selection logic of the "Next disk" feature (`VD_NEXT_DISK` in `../vdrives.asm`), which mounts the image that follows the mounted one in its folder: the start cluster that `DIRBROWSE_READ` (`../dirbrowse.asm`) stores in every list element and the ring walk of `DIRBROWSE_NEXT`. The runner builds an MBR plus FAT32 image with long file names, hidden files, number-like names, folders named like disk images, a directory that spans several clusters and lower case 8.3 names, attaches it to the emulator as the SD card (`-a`) and compares the output with an independent Python model of the file browser: the C64 file filter, the sort order (folders first, case insensitive, numbers by length), the current image, the next image with wrap-around and the complete ring, including a mounted image that is not part of the folder and folders with one or no image. Run it with `python3 next_disk_test.py`.
* **`bankdepth_test.py`** — static regression gate for the register bank nesting depth of the firmware. Every `INCRB` takes one register bank and every `SYSCALL(enter, 1)` takes two, but the hardware has only `SHADOW_REGFILE_SIZE` banks (`M2M/vhdl/QNICE/qnice_globals.vhd`): one level too many silently overwrites the registers of a routine further up the call chain. The QNICE emulator has 256 banks, so no testbed can notice this. The test preprocesses `CORE/m2m-rom/m2m-rom.asm`, follows every path of every routine and prints the worst case per scenario (boot, main loop, visible menu, debug Monitor, each keyboard shortcut). It fails if the deepest level leaves fewer than `MIN_MARGIN` banks free, if a routine returns at the wrong level, or if a new indirect call is missing from its table `INDIRECT`. Run `python3 bankdepth_test.py` (needs only `cc`, a few seconds) after changing Shell or Monitor code; every `FAIL` line says what to do, `--report` shows the deepest chains hop by hop and `--selftest` checks the test itself.
* **`llist_test.asm`** — testbed for the sorted doubly-linked list (`../llist.asm`) used by the file browser: inserts 500 fixed test strings, prints them unsorted, ascending and descending. Runs headlessly.
* **`dirbrowse_test.asm`** — development testbed for the directory browser (`../dirbrowse.asm`). Needs SD-card/FAT32 hardware devices, so it is meant for the MEGA65 hardware or a full-system simulation, not for the plain emulator.
* **`keyboard_test.asm`** — development testbed for the MEGA65 keyboard driver (`../keyboard.asm`). Hardware-bound like `dirbrowse_test.asm`.

String ROM tests
----------------

In a release build, `CORE/m2m-rom/make_rom.sh` assembles the firmware with `M2M/tools/asm_strrom.sh`: the strings between the marker comments `;STRROM_BEGIN` and `;STRROM_END` go into the string ROM (`CORE/m2m-rom/m2m-strings.rom`), and their labels become handles (see `../strrom.asm`). Two tests guard this build:

```bash
python3 M2M/rom/tests/strrom_test.py               # build + verify (about 10 s)
python3 M2M/rom/tests/strrom_test.py --no-build    # verify the last build only
python3 M2M/rom/tests/strrom_test.py --report      # also list the strings that are still in the firmware ROM
python3 M2M/rom/tests/strrom_tool_test.py          # fixtures for asm_strrom.sh itself (about 6 s)
```

**`strrom_test.py`** runs `make_rom.sh` and then verifies the artifacts without reusing anything of `asm_strrom.sh`, so it also proves on the Linux build machine (with another awk and another C preprocessor) that the build produced the right files. It assembles a reference firmware itself, with all strings in place, and runs four checks:

* **strings** — every table entry between `STRROM$TAB` and `STRROM$TAB_END` leads to the same zero-terminated string in `m2m-strings.rom` as its label in the reference firmware; every label and every word of every marked section is covered.
* **transform** — the listings of both builds contain the same source lines, except for the lines between the markers (removed) and the table lines behind `;STRROM_TABLE` (added). This proves that no other line was dropped or changed.
* **layout** — `m2m-strings.rom` has `2**C_STRROM_ADDR_WIDTH` lines of two hexadecimal digits (`M2M/vhdl/qnice_wrapper.vhd`), no string crosses a 4k window, everything outside of the strings is zero, and strings only overlap where labels point into the same string in the sources.
* **handles** — a lint over the firmware source as the assembler sees it: every use of a handle must reach a handle-aware routine (`SYSCALL(puts, 1)`, `LOG_STR`, `SCR$PRINTSTR`, `SCR$PRINTSTRXY`, `FATAL`, `FATAL_IDX`). The simple pattern (`MOVE <label>, R8`, then only instructions that leave R8 alone, then an unconditional call of a handle-aware routine) is accepted automatically. Every other use needs an entry in `ALLOWLIST` inside the test, which records the code around the use and the code it flows through (`PINS`); both were proven safe by hand. The lint also checks that the handle-aware routines still call `STRROM$OPEN` and `STRROM$CLOSE` and that the fatal callback of the menu is still `FATAL`.

If the handle lint fails after you changed the firmware, read the message: either you passed a handle to code that needs a pointer (for example `strlen`, `strcpy`, `M2M$RPL_S`, `OPTM_LIVE_TEXT` or a direct `@Rx` read) — then move the string above the `;STRROM_BEGIN` marker — or you wrote a new, safe use that the lint cannot prove by itself — then check every consumer and add an `ALLOWLIST` entry. A failing pin means that code which carries handles changed; check the entries that name the pin in `via` again and update the pin.

`--report` lists the strings that are still part of the firmware ROM, largest first, together with the reason why they stay there. Strings marked `CANDIDATE` only reach handle-aware routines and could move into the string ROM (a move saves the size of the string minus one table word).

**`strrom_tool_test.py`** feeds `asm_strrom.sh` with about 50 small fixture programs: correct and broken marker structures, every kind of line between the markers, strings that fill, overflow and pad the 4k windows, CRLF line endings, special characters, wrong arguments, and a directory with a space in its name. Every broken fixture must end with exit code 1, an error that names the problem, and neither `<firmware>.rom` nor `<strings>.rom`; for every correct fixture the string ROM must match what the assembler produces with the strings in place. Run it after every change of `asm_strrom.sh`.

Both tests write their temporary files into the system temporary directory; `strrom_test.py` regenerates the usual build artifacts in `CORE/m2m-rom`.

The string ROM test (simulated hardware)
----------------------------------------

**`strrom_sim_test.py`** is the regression gate for the string ROM: the firmware side in `../strrom.asm`, the build tool `M2M/tools/asm_strrom.sh` and the QNICE device `M2M$STRROM` in `M2M/vhdl/qnice_wrapper.vhd`. The QNICE emulator has no M2M devices, so this is the one test of this folder that does not run in the emulator. It runs on **simulated hardware** instead: [ghdl](https://github.com/ghdl/ghdl) simulates the real QNICE CPU inside the real `qnice_wrapper.vhd`, with the real device decoding and the real string ROM block RAM, preloaded from the very file that `asm_strrom.sh` has written. Still no MEGA65, no JTAG cable and no Vivado; if ghdl is not installed, the test says so and skips.

```bash
python3 M2M/rom/tests/strrom_sim_test.py            # four simulations in parallel: one to two minutes
python3 M2M/rom/tests/strrom_sim_test.py --jobs 1   # one simulation: about 2.5 minutes on an idle computer
python3 M2M/rom/tests/strrom_sim_test.py --full     # every string through every output routine: 2.5 times the work
```

Run it before you synthesize a bitstream after touching `strrom.asm`, `asm_strrom.sh`, the string ROM in `qnice_wrapper.vhd` or one of the routines that accept the handle of a string ROM string: `IO$PUTS` in `../monitor/io_library_m2m.asm`, `LOG_STR` in `../tools.asm` and `SCR$PRINTSTR` in `../screen.asm`.

The test consists of three files:

* **`strrom_sim_test.asm`** — the firmware of the test. It is built exactly like the real firmware: as a release-style ROM with the QNICE Monitor at 0x0000, by `asm_strrom.sh` and with the address width that `qnice_wrapper.vhd` defines. It contains the real `../tools.asm` and `../screen.asm` and it does not check anything by itself: it reports what it reads from the string ROM and what the routines under test do, and the runner compares that with its own expectations.
* **`strrom_sim_tb.vhd`** — the testbench around `qnice_wrapper`, with the video RAM of the on-screen menu instantiated and wired like in `av_pipeline.vhd` and `framework.vhd` and with a RAM as an example of a device of the core. It also contains a second architecture of the UART of QNICE that wraps the real one: this is how the firmware reports to the testbench (three write-only ports in the address range of the UART that the real UART ignores) and how the test gets around the 115,200 baud of the real UART, which costs 4,752 simulated clock cycles per character. A few strings are transmitted by the real UART and decoded from its pin; after that the firmware switches the wrapper to a turbo mode that takes the characters from the transmit register.
* **`strrom_sim_test.py`** — the runner. It contains the **model**: a parser of its own for the string ROM sections of the preprocessed sources, a placement of its own (no string crosses a 4k window) and instruction-level models of `STRROM$OPEN`, `IO$PUTS`, `LOG_STR` and `SCR$PRINTSTR`. Every expected value is derived from the sources and compared twice: with the outputs of `asm_strrom.sh` before the simulation starts, and line by line with the output of the simulation while it runs.

The string ROM of the test contains **every string ROM string of the Shell** — the runner collects the marked sections of all Shell sources, including the ones of the core in `CORE/m2m-rom/` — plus strings for the edge cases: the empty string, a single character, CR/LF, the special characters of `SCR$PRINTSTR`, labels in the middle of a string, characters above 0x7F, a string that ends at the last address of a 4k window, a string that is one character too long for the rest of its window and a string of 4095 characters that fills a whole window. The edge cases that depend on positions are created by filler strings whose lengths are computed on every run from the current lengths of the real strings (`strrom_sim_fixtures.asm`), so the test does not break when messages are added or changed. The runner prints the resulting layout and fails if an edge case got lost.

What is checked:

* **Build** — the string ROM image and the table of handles that `asm_strrom.sh` produces are equal to what the model derives from the sources, and the file names that the hardware opens are the outputs of `make_rom.sh`.
* **Device** — every word of all 4k windows of the string ROM as QNICE reads it, the windows behind the end of the string ROM, and that write accesses are ignored.
* **`STRROM$OPEN` and `STRROM$CLOSE`** — for every handle and for values at and around the limits of the table that are no handles: R8, the selected device and window, the stack pointer, the registers of the caller and the Carry and the Overflow flag, which neither routine may change (every value is tested with both flags set and with both flags clear), with twelve different devices and windows selected before the call, one of them a device that never answers in the testbench, so that an access to the 4k window at the wrong time gets stuck and is reported; nested calls; and every handle is read through `STRROM$OPEN` up to its terminator.
* **`IO$PUTS`, `LOG_STR` and `SCR$PRINTSTR`** — the characters at the UART and in the video RAM (each write access and the content as the video output would read it), R8, the selected device and window and the stack pointer after the call; for `IO$PUTS` also the Carry and the Overflow flag, which it preserves (`LOG_STR` and `SCR$PRINTSTR` never did, so nothing is pinned there). Every handle runs through one of the three routines, the strings for the edge cases and the ordinary strings (in ROM, in RAM, in the window of a device of the core and in the window of `config.vhd`) through all of them. `--full` runs every handle through all three.

The simulation is slow: about 20,000 clock cycles per second on an idle computer and a third of that when all cores are busy, and the test needs 2.9 million of them. Therefore the runner splits the work into simulations that run in parallel (`--jobs`, 1 to 5; the default is four on a computer with at least eight logical processors); the split is balanced by measured costs and each simulation gets its share of the test via a table in the firmware.

When the test fails, it names the string, the routine and the first line that differs. For a closer look, `strrom_sim_job<N>.exp` and `strrom_sim_job<N>.got` contain the expected and the actual output of each simulation and can be compared with `diff`; `--keep` keeps the work directory of ghdl. All these files, the assembler outputs and `strrom_sim_fixtures.asm` are generated on every run.

The strings of the test contain characters above 0x7F on purpose, so that all eight data bits of the string ROM are exercised. That only works because the build processes the sources byte by byte in the C locale (`LC_ALL=C`); the runner sets it for everything it starts.

Running a testbed manually
--------------------------

```bash
( cd M2M/rom/tests && ../../QNICE/assembler/asm llist_test.asm )
M2M/QNICE/emulator/qnice -b 0x8000 \
    M2M/QNICE/monitor/monitor.out M2M/rom/tests/llist_test.out < /dev/null
```

`-b` loads the listed `.out` files, sets up SP/PC like the Monitor cold start and runs until `HALT` or stdin EOF. Programs that use `SYSCALL`s need `monitor.out` loaded alongside, as shown. A runaway program that never reads stdin spins forever, so wrap emulator calls in a timeout when scripting (`menu_test.py` does this for you).
